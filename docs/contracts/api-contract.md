> Proposed local HTTP contract for the approved Node.js/Express/TypeScript
> application. No endpoint exists in code yet. Paths, status codes, field
> names, and error envelope require human review; they do not resolve the
> product decisions listed below.

## Conventions and local access

- JSON is used for API metadata and responses. CSV upload uses
  `multipart/form-data` with one file part named `file` (proposed).
- IDs are opaque strings generated by the backend. Exact format is not part of
  the public contract.
- Case status values are exactly `Pending`, `Reviewed`, and `Escalated`.
- A single local user is assumed; authentication and role-based access are
  out of scope. The API is not authorized for remote exposure.
- The API must not accept or return numeric risk probabilities, accusations,
  or automated financial decisions.
- The database is accessed only by Express. Successful import writes and
  generated records commit together. A status change and its audit event
  commit together. A failed write is an error, not a success response.

## Proposed error envelope

```json
{
  "error": {
    "code": "IMPORT_VALIDATION_FAILED",
    "message": "The CSV was rejected. Correct the reported issues and retry.",
    "details": {
      "rowErrors": [
        { "row": 4, "field": "proposed-column", "code": "INVALID_VALUE", "message": "Value is invalid." }
      ]
    }
  }
}
```

The envelope and codes are proposals. Messages must be actionable without
echoing sensitive values or exposing stack traces. A row error identifies the
CSV row and issue; a file-level error identifies the structural issue where
row number is not applicable. Do not include uploaded row contents in
operational errors or claim a rejected import succeeded.

## Endpoint proposals

| Method and path | Purpose | Access assumption |
|---|---|---|
| `POST /api/imports` | Validate and accept one synthetic CSV; analyze and persist accepted records and generated flags/evidence | Local user |
| `GET /api/dashboard` | Return the agreed summary counts and empty-dataset state | Local user |
| `GET /api/transactions` | List transactions with applicable filters | Local user |
| `GET /api/transactions/{transactionId}` | Retrieve one accepted transaction by internal ID | Local user |
| `GET /api/flags` | List flags with applicable filters | Local user |
| `GET /api/flags/{flagId}` | Retrieve a flag, explanation, and supporting transaction references | Local user |
| `POST /api/flags/{flagId}/cases` | Manually create one case for a flag | Local user |
| `GET /api/cases` | List cases, optionally filtered by status | Local user |
| `GET /api/cases/{caseId}` | Retrieve case, linked flag/evidence, and available audit history | Local user |
| `PATCH /api/cases/{caseId}/status` | Apply one permitted human-selected status change | Local user |

No endpoint performs automatic accusation, escalation, blocking, or a
financial decision. No automatic startup re-analysis endpoint is included.
An explicit re-analysis operation, if ever proposed, requires a separate
review and behavior definition.

## Import contract

### `POST /api/imports`

**Request:** `multipart/form-data`, one `file` part containing CSV. Synthetic
data only. The accepted columns, encoding, timestamp rules, currency/amount
semantics, duplicate handling, size, and row limit are deliberately not
defined here; the approved CSV contract must settle them before implementation.

**Processing:** Validate file structure and every row before persistence. On
any validation error, reject the whole submission and persist none of its
transactions or generated records. For a valid file, write the accepted
import, transactions, generated flags, and evidence links in one SQLite
transaction. Do not report success before commit. A database or analysis
failure returns an operation failure and must not masquerade as acceptance.

**Proposed success (`201 Created`):**

```json
{
  "importId": "opaque-id",
  "acceptedTransactionCount": 12,
  "generatedFlagCount": 3
}
```

Counts are illustrative shape only. The response describes this submission;
it does not decide whether multiple imports combine for later dashboard or
detection queries.

**Proposed failure behavior:**

- `400` for invalid structure or row validation, with row-level errors.
- `413` may represent a future approved capacity limit; no limit or overflow
  behavior is currently defined, so this status is not yet a settled
  requirement.
- `500` for unexpected processing or persistence failure, with a generic
  non-sensitive message.

The implementation must ensure rejected input changes no previously accepted
records. Whether rejected-attempt metadata is retained is open.

## Summaries, lists, and filters

### `GET /api/dashboard`

Return counts for accepted transactions, distinct flags, flags by each of the
four rule categories, and cases by all three statuses (including zeroes).
With no accepted dataset, return an explicit empty state rather than
fabricated counts. Rejected imports contribute no transactions or flags.
Multiple-import scope remains unresolved; the API must not choose a
combine-or-select policy without human approval.

Proposed response shape:

```json
{
  "hasAcceptedDataset": true,
  "transactionCount": 12,
  "flagCount": 3,
  "flagsByCategory": {
    "rapid_fund_movement": 1,
    "repeated_transfers": 1,
    "circular_flows": 1,
    "structuring_like": 0
  },
  "casesByStatus": {
    "Pending": 1,
    "Reviewed": 0,
    "Escalated": 0
  }
}
```

Counts are illustrative, not a fixture result. The empty-state response
shape/copy and the dataset scope used for counts need review.

### `GET /api/transactions` and `GET /api/flags`

Proposed query parameters:

| Parameter | Meaning |
|---|---|
| `dateFrom`, `dateTo` | Inclusive selected date range |
| `amountMin`, `amountMax` | Inclusive amount range |
| `ruleCategory` | One rule category |
| `caseStatus` | `Pending`, `Reviewed`, or `Escalated` |
| `flagged` | Transaction view only: `true` or `false` |

Multiple applicable active filters combine using AND. One value/range per
dimension is active per view. Apply the approved FRD semantics:

- Transaction date and amount ranges apply to each transaction. `flagged`
  selects transactions with at least one flag or no flags. Category selects a
  transaction with at least one flag in that category.
- Flag category applies to the flag. Date and amount match only when the same
  supporting transaction satisfies both active ranges. `flagged` is not
  applicable.
- A case-status filter on a transaction or flag returns only items linked
  through a flag to a case with that status; unlinked items are excluded.
- Cases support case status; other listed filters are not applicable.
- Range endpoints are inclusive; transaction timestamp/time-zone parsing
  remains dependent on the approved CSV contract.
- Clearing filters restores all items in that view. No matches produce a
  no-results response distinct from an empty dataset or failure.

Reject malformed or inapplicable query values with a validation error rather
than silently ignoring them (proposed). Ordering and pagination are open; do
not invent default ordering or page limits here.

### Transaction and flag details

`GET /api/transactions/{transactionId}` returns the requested stored
transaction or `404`. `GET /api/flags/{flagId}` returns a flag with:

```json
{
  "id": "opaque-id",
  "category": "rapid_fund_movement",
  "explanation": "A configured rule matched these synthetic transactions.",
  "generatedAt": "timestamp",
  "supportingTransactions": [
    { "id": "opaque-transaction-id", "sourceTransactionId": "synthetic-reference" }
  ]
}
```

Names and values are illustrative. Each flag must have an understandable
reason and resolvable supporting transaction references. Do not include a
numeric score or describe a flag as proof.

List requests return a proposed `{ "items": [...] }` envelope. Transaction
items use the `transaction` fields in the Data Model. Flag items use the
`risk_flag` fields and include evidence references through `flag_evidence`.
These are proposals pending the combined Data Model/API review, including
field names and nullability. Pagination and ordering are not defined. Missing
detail IDs return `404`; list or detail read failures return an error, not a
success-shaped empty list.

## Cases and audit behavior

### `POST /api/flags/{flagId}/cases`

Create a case only after an explicit human action. The request has no status
field; the server initializes status to `Pending`. A second create attempt
for a flag with an existing case creates nothing and returns a conflict with
the existing case reference (proposed `409`). A successful response returns
the created case. Case creation itself is not an approved mandatory audit
event: returning a creation audit entry is optional proposed behavior pending
human decision. Persist cases and audit events that are recorded so they
survive restart.

### `PATCH /api/cases/{caseId}/status`

Request:

```json
{ "status": "Reviewed" }
```

Accept only the exact three status strings. From each current state, permit
the other two states: Pending→Reviewed/Escalated, Reviewed→Pending/Escalated,
Escalated→Pending/Reviewed. Selecting the current status is a no-op: return
the unchanged status and create no status-change audit event. For an actual
change, atomically persist the new status and audit event. If either write
fails, return failure and do not represent the change as completed.

Proposed success (`200 OK`) returns the case representation shown below and
`unchanged: true|false`. `true` means no status-change audit event was created;
`false` means the status and corresponding event committed atomically.

Every audit event contains timestamp, action, and actor label. Status-change
events also contain previous and new status. Actor-label value/format and
additional audited actions remain open. The actor label is not proof of an
authenticated identity.

Responses expose available persisted audit history; retention, deletion,
backup, and recovery policies remain open. Audit retrieval or write failure
must be presented as failure, not success-shaped empty history.

Proposed case representation:

```json
{
  "id": "opaque-case-id",
  "flagId": "opaque-flag-id",
  "status": "Pending",
  "createdAt": "timestamp",
  "updatedAt": "timestamp",
  "auditEvents": []
}
```

`GET /api/cases/{caseId}` returns this representation with the case's
available `auditEvents` (`200 OK`), or `404` if the case does not exist.
`GET /api/cases?caseStatus=...` returns `200 OK` with
`{ "items": [case representations] }`; absent `caseStatus` returns all
available cases. Ordering and pagination remain open. Audit read failure
fails the request; it must not be represented as an empty event list.

`POST /api/flags/{flagId}/cases` returns `201 Created` with the created case
representation. If the flag does not exist, return `404`. If a case already
exists, return `409` with the existing case ID and create no duplicate. A
creation audit event is not guaranteed by this contract; decide separately
whether to record it and include it in the response.

`PATCH /api/cases/{caseId}/status` returns `200 OK` with the case
representation and `unchanged`. Return `404` for a missing case and `400`
for an invalid status. A persistence/audit transaction failure returns
`500`; do not claim the change succeeded. The response must only include a
status-change event after that event commits.

## Error status proposals

| Status | Proposed use |
|---|---|
| `400` | Invalid request, query, CSV structure, or row validation |
| `404` | Requested transaction, flag, or case does not exist |
| `409` | A case already exists for the flag |
| `500` | Unexpected processing, database, or audit operation failure |

This table proposes protocol mapping; exact error codes, message copy, and
unexpected-failure handling need implementation review. Do not expose SQL,
stack traces, secrets, or submitted sensitive values. No real customer data
is permitted.

All errors use the proposed error envelope above. Validation errors include
actionable details where applicable; `404` and `409` identify the resource or
conflict without disclosing unrelated data; `500` uses a generic message.
For every persistence failure, the operation returns an error and the
documented atomic write leaves no partial success. Do not return an empty
success list or success-shaped resource on a failed read/write.

### Amount-filter currency constraint

The approved filter includes an inclusive amount range, but currency
semantics remain unresolved. Implementations must not compare or combine
amounts across currencies. The currency selection/partition behavior must be
defined in the CSV contract and reviewed before amount-filter behavior is
implemented; no `currency` parameter or default currency is fixed here.

## Open decisions

- CSV contract and row semantics, duplicate transaction ID behavior, limits,
  oversized-file behavior, parser, and error detail vocabulary.
- Rule thresholds, time windows, matching/boundary semantics, and rule
  configuration interface.
- Multiple-import dataset selection/combination for dashboard and lists.
- Query ordering, pagination, and response size controls.
- Currency semantics and how an amount range is scoped to a currency; do not
  compare values across currencies.
- Actor-label source/format and the additional actions included in audit.
- Audit retention, backup, recovery, deletion, and rejected-attempt metadata.
- Node.js runtime and compatible SQLite driver; exact error/status mapping.
- Performance targets, local resource limits, and test runner/coverage.
